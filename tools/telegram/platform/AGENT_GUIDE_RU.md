# Гайд Агента По Центру Управления Telegram

Этот документ нужен новому агенту, который работает именно с Telegram control center слоем.

## Что Это За Слой

`tools/telegram/platform` — это registry-driven control layer для локальных Telegram workflow.

Он нужен, чтобы:
- отдельные инструменты оставались самостоятельными;
- новые инструменты можно было добавлять без переписывания GUI;
- агент видел не просто разрозненные скрипты, а структурированный catalog;
- оператор мог выбирать нужного Telegram portable-пользователя без ручного ввода путей;
- оператор видел только два понятных рабочих режима:
  - `Добавить контакты из TXT`
  - `Сессия и сообщения`

## Что Считать Источником Правды

1. `registry/tools.json`
2. `tool_manifest.json` каждого подключённого инструмента
3. `tool_platform/catalog.py`
4. `tool_platform/cli.py`
5. `tool_platform/gui.py`
6. `tool_platform/telegram_profiles.py`

## Как Добавлять Новый Инструмент

1. Не тащить runtime инструмента прямо в GUI-код.
2. Создать рядом с инструментом `tool_manifest.json`.
3. В manifest указать:
   - `tool_id`
   - `display_name`
   - `root_dir`
   - docs paths
   - operator actions
4. Добавить путь к manifest в `registry/tools.json`.
5. Обновить `README_RU.md`, если инструмент значимый для оператора.
6. Если инструмент использует Telegram Desktop portable actor, подумать, нужен ли ему выбор профиля из общей панели, а не отдельная форма.
7. Если инструмент должен появиться как отдельная большая кнопка в панели, это нужно явно описать в docs и держать UX простым.

## Как Сейчас Устроен Первый Режим

Первый большой режим панели теперь не должен трактоваться как "invite-job creator".
Его текущий контракт другой:
- оператор выбирает portable-профиль сверху;
- загружает `.txt/.csv/.json` список username;
- нажимает `Старт добавления`;
- панель запускает `telegram_invite_executor.py desktop-add-contact-batch`;
- batch-команда сама создаёт local state, настраивает portable actor и по очереди вызывает существующий one-user путь `desktop-add-contact-profile`.

Если агент меняет этот режим, он обязан сохранить именно эту модель:
- простой выбор файла с компьютера;
- одна явная кнопка запуска;
- отдельные кнопки `Продолжить очередь`, `Повторить ошибки`, `Статус задачи`, `Что осталось`, `Стоп`;
- видимую очередь, успешно добавленные контакты, ошибки и историю batch-запусков;
- отсутствие путаницы между добавлением в личные контакты и инвайтом в чат.

## Как Сейчас Устроен Второй Режим

Второй режим панели управляет именно `telegram_session_runner`.

Его текущий контракт:
- оператор выбирает portable-профиль сверху;
- загружает session-config;
- видит и может править список адресатов;
- задаёт тексты сообщений;
- задаёт random-walk визиты и интервалы, сколько сообщений слать за цикл и общий лимит;
- может крутить сессию либо один цикл, либо непрерывно до `Стоп`;
- после запуска видит сводку по последнему run, историю запусков и явные признаки, если сообщение осталось неотправленным.

Если агент меняет этот режим, он обязан сохранить:
- отдельность от contact-add режима;
- понятные поля `кому писать / что писать / сколько раз / как долго идти`;
- видимую историю отправок без необходимости вручную открывать `run.json`.

## Что Нельзя Делать

- Нельзя ломать standalone-режим инструмента ради unified panel.
- Нельзя превращать platform layer в место, где живёт Telegram-specific runtime logic.
- Нельзя плодить отдельные сложные экраны там, где хватает простого profile-first управления и двух понятных режимов.

## Следующий Масштабируемый Шаг

Если появится ещё один локальный инструмент, правильный путь:
- сохранить его как отдельную единицу;
- дать ему свой manifest;
- зарегистрировать его в `tools/telegram/platform/registry/tools.json`;
- отдельно решить, нужен ли ему собственный операторский режим в панели или достаточно CLI/registry слоя.
