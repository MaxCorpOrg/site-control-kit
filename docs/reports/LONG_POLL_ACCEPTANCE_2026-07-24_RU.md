# Приёмка сервисных границ и долгого запроса

Дата: 24 июля 2026 года.

## Что проверено

- HTTP вызывает команды, клиентов, сессии и состояние через `HubServices`;
- постановка команды будит ожидающий `CommandService`;
- старый маршрут без `wait_ms` немедленно возвращает `command: null`;
- неверный `wait_ms` получает стабильную ошибку;
- расширение держит только один запрос команд;
- после ответа оно сразу открывает следующий запрос;
- ошибка соединения использует настраиваемую задержку;
- остановка MV3 service worker и перезапуск хаба по-прежнему восстанавливаются.

## Модульные доказательства

Контрактный тест ждёт команду в отдельном потоке, ставит её через
`CommandService` и требует пробуждения менее чем за 500 мс. Отдельно
проверяются тайм-аут, немедленный совместимый режим, URL расширения и задержка
после ошибки.

## Реальный Chrome

Chrome for Testing `151.0.7922.47`, расширение `0.3.0`, протокол `2.1`.

Результат:

```json
{
  "status": "passed",
  "test_count": 17,
  "passed": 17,
  "failed": 0,
  "p50_delivery_ms": 13.62,
  "max_delivery_ms": 19.41,
  "lost_acknowledged_commands": 0,
  "duplicate_dangerous_actions": 0,
  "recoveries": 2
}
```

Время доставки измеряется между переходами `queued` и `leased`, а не по
полному времени DOM-действия. Сырой `report.json`, журналы и снимок не
коммитятся; CI создаёт их заново как временный артефакт.

Один прогон доказывает контракт и целевой порог, но не статистическую
надёжность 99%. Для неё в дорожной карте остаётся серия из 100 прогонов.

## Остаточный риск

- каждый долгий запрос занимает поток `ThreadingHTTPServer`;
- доменная логика ещё физически находится в `store.py`;
- `background.js` всё ещё совмещает вкладки, фреймы, CDP и outbox;
- при большом удалённом парке нужен событийный сервер и лимит подключений.
