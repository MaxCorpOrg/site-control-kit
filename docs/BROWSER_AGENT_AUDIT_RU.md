# Аудит управления браузером для ИИ-агентов

Дата исследования: 2026-07-24.

Неизбежные технические термины объяснены в [словаре](TERMS_RU.md).

## Короткий вывод

`site-control-kit` уже занимает полезную нишу, которую не закрывают обычные
сценарии Playwright: он подключается к реальному, видимому и уже
авторизованному браузеру оператора, сохраняет ручной контроль и имеет простой
локальный хаб. Это сильная основа для агентов, работающих вместе с оператором.

Главный разрыв с современными инструментами для агентов был не в количестве
DOM-команд, а в уровне абстракции:

- агент видел сырой текст/HTML вместо компактной семантической модели страницы;
- действия зависели от CSS-селекторов и не проверяли готовность элемента;
- доставка не имела аренды и повторной выдачи, а результат терялся при обрыве после
  выполнения команды;
- вкладки существовали как поля цели, но не как изолированные сессии агента;
- отсутствовали трассы браузера, сети и консоли, воспроизведение и сквозной
  контур.

Первый срез P0 из этого документа уже реализован: семантический снимок, ссылки
`ref`, семантические локаторы, умные ожидания, схема агента, взаимоисключающий
опрос, очередь результатов, корректный снимок выбранной вкладки и проверка
результата.

### Что следует перенять

1. Из Playwright: семантику локаторов, готовность к действию, изоляцию
   контекстов, сохранение состояния и трассу как единый артефакт.
2. Из agent-browser и MCP-инструментов: компактный snapshot с refs и
   машиночитаемую схему.
3. Из browser-use: долговечный протокол событий и результатов, переподключение,
   восстановление,
   идемпотентное наблюдение.
4. Из Webwright: каждый запуск должен оставлять сценарии, журналы и снимки, пригодные
   для повторения.
5. Из BrowserGym/WebArena: проверять не только факт выполнения команды, а
   конечное состояние задачи.

## Аудит текущего `site-control-kit`

### Сильные стороны

- Локальный хаб с минимумом зависимостей и прозрачный `state.json`.
- Реальный профиль браузера: уже выполненная человеком авторизация, файлы cookie,
  2FA и ручное продолжение остаются доступными.
- Видимый операторский сценарий и восстановление через X11/noVNC.
- Стабильные идентификаторы команд, сигнал активности, объявление возможностей, команды уровня
  вкладки и DOM.
- Безопасный явный выбор клиента в `sitectl browser`, поддержка нескольких
  подключённых extension clients.
- Сильный прикладной контур Telegram с артефактами запусков и историей — полезный
  образец наблюдаемости для общего браузерного слоя.
- Уже выданное расширению разрешение `debugger` позволяет постепенно добавить
  CDP observability без замены всего bridge.

### Узкие места до P0-среза

#### Наблюдение и динамический DOM

- `extract_text` и `get_html` слишком объёмны для цикла агента и не дают
  устойчивых идентификаторов действий.
- Базовый `queryElement` знает только CSS и при нескольких совпадениях выбирает
  элемент по z-index/расстоянию. Результат может меняться от layout.
- Нет локаторов по роли, имени, подписи, заполнителю и `test-id`, обхода Shadow DOM и
  безопасного строгого режима.
- После React/Vue re-render старый DOM node не восстанавливался.

#### Ожидания и действия

- `wait_selector` проверял существование и слабую видимость.
- `click` не проверял stability, enabled и перекрытие другим элементом.
- `navigate`, `reload`, `new_tab`, history переходы завершались до готовности
  новой страницы.
- Нет ожиданий URL, network idle, DOM quiet, popup/download/dialog.

#### Надёжность транспорта

- Одновременно могли идти interval/alarm/popup polls.
- Hub удаляет command ID из FIFO в момент dispatch. Lease, ack и redelivery
  отсутствуют; падение MV3 worker после получения теряет выполнение.
- Результат отправлялся один раз. Обрыв после side effect оставлял delivery в
  `dispatched` до expiration.
- Hub раньше принимал result от клиента, которому команда не назначалась, и
  позволял позднему result перезаписать terminal delivery.
- `state.json` полностью переписывается на heartbeat, dispatch и read; commands
  не имеют retention/compaction.

#### Вкладки, браузеры и сессии

- Tab — только target, а не session с ownership, mutex, policy и artifact
  directory.
- Нет page event stream; heartbeat snapshot может отставать.
- Нет browser lifecycle API, isolated contexts, profile manager, Firefox/WebKit
  adapter и remote workers.
- При прежней реализации screenshot мог вернуть активную вкладку того же окна,
  а не явно выбранный background tab.

#### Наблюдаемость и безопасность

- Нет console/network logs, HAR, trace, DOM snapshots на ошибке и video.
- CORS разрешён широко, query-token поддерживается для удобства, extension имеет
  `<all_urls>` и `debugger`: это локальный trusted tool, а не security boundary.
- Нет domain allow/deny policy, secret redaction и per-agent capability grants.
- `run_script` зависит от CSP/контекста и представляет отдельную опасную
  capability.

#### Поддерживаемость и тесты

- `webcontrol/cli.py` совмещает protocol payloads, operator UX и X11 fallback.
- Browser semantics находились в одном `content.js`.
- Python hub хорошо покрыт unit-тестами, но extension JS и реальный Chrome не
  входят в автоматический regression suite.

## Реализованный P0-фундамент

### Модуль агентного DOM `extension/agent_dom.js`

Новый слой не меняет legacy CSS-команды и предоставляет:

- компактный semantic snapshot с `e1`, `e2`, ...;
- локаторы `css`, `ref`, `role + accessible name`, `text`, `label`,
  `placeholder`, `test_id`;
- strict matching и явный `nth`;
- traversal открытых Shadow DOM;
- page-lifetime refs и уникальное healing по id/test-id/role+name/placeholder;
- состояния `attached`, `detached`, `visible`, `hidden`, `enabled`, `editable`,
  `stable`, `actionable`, `text`, `value`;
- actionability: attached, visible, enabled, editable, receives-events,
  стабильный bounding box.

Schema v1 намеренно ограничена top frame. Cross-origin iframe routing требует
отдельного frame-aware protocol, а не неявного выбора.

### API агента и командный интерфейс

- `GET /api/agent/schema`;
- `sitectl browser schema`;
- `sitectl browser snapshot`;
- `sitectl browser smart-click`;
- `sitectl browser set-text`;
- `sitectl browser wait-for`.

Payload builder вынесен в `webcontrol/browser_agent.py`, чтобы следующий SDK или
MCP adapter использовал один контракт с CLI.

### Надёжность

- Одновременно выполняется не больше одного poll и одного heartbeat.
- Результат сначала сохраняется в `chrome.storage.local`, затем отправляется
  hub. Outbox повторяется до успеха и блокирует получение следующей команды,
  сохраняя порядок.
- Время выполнения `finished_at` приходит от browser client отдельно от
  hub-side `received_at`, поэтому задержанная outbox-доставка не искажает
  длительность действия.
- Повторный result идемпотентен; foreign client и неизвестный status
  отклоняются; terminal delivery не перезаписывается.
- Screenshot явно выбранной вкладки делается через
  `Page.captureScreenshot`; active-tab API остался только fallback.
- Повторная инъекция content script защищена guard, а auto-inject загружает
  agent DOM module до command listener.

### Осознанно не решено в этом срезе

- Outbox закрывает потерю результата, но не падение между dispatch и первым
  сохранением result.
- Refs действуют только внутри текущего document lifecycle.
- Реализация accessible name — практичный subset, не полный W3C ACCNAME.
- Mutation/network navigation readiness и frame routing ещё отсутствуют.
- Нет защиты от двух независимых агентов, одновременно управляющих одной
  вкладкой.

## Целевая модульная архитектура

```text
Агент / командный интерфейс / будущий MCP
          |
          v
Схема API агента + типизированные команды
          |
          v
Слой управления: авторизация, клиенты, сессии, аренды, идемпотентность
          |
          +-------------------+
          |                   |
          v                   v
Адаптер расширения      Адаптер исполнителя Playwright/CDP
(живой браузер)         (изолированные/удалённые браузеры)
          |                   |
          +---------+---------+
                    v
 Контракты наблюдения, локатора и готовности к действию
                    |
                    v
 Поток артефактов и событий: команды, консоль, сеть, трасса, снимки, видео
```

Границы модулей:

1. `webcontrol/protocol/` — версионированные схемы, проверка и совместимость.
2. `webcontrol/control/` — клиенты, сессии, очереди, аренды, блокировки и срок хранения.
3. `webcontrol/adapters/` — исполнители расширения, CDP и Playwright с общей
   моделью возможностей.
4. `extension/agent_dom.js` — только наблюдение DOM, локаторы и готовность к действию.
5. `extension/background.js` — транспорт, жизненный цикл вкладки, адаптер CDP и
   долговечная очередь результатов, без знания командного интерфейса.
6. `webcontrol/artifacts/` — только дописываемые события и каталоги запусков.
7. `webcontrol/policy/` — правила доменов, опасные возможности и скрытие секретов.
8. `webcontrol/sdk/` — клиент Python; MCP и другие интерфейсы являются тонкими
   адаптерами поверх схемы.

Ключевой инвариант: оболочка команды не должна зависеть от конкретного драйвера.
Адаптер публикует возможности, а хаб проверяет, что выбранная сессия
поддерживает нужную команду.

## Дорожная карта

Сложность: `S` — до нескольких дней, `M` — примерно неделя, `L` — несколько
недель, `XL` — отдельный проектный этап. Оценки относительные и требуют
пересмотра после design spike.

| Приоритет | Блок | Сложность | Зависимости | Критерий готовности |
|---|---|---:|---|---|
| P0, готово | Снимок, ссылки, семантические локаторы, умные ожидания и действия | M | Нет | Быстрая проверка проходит без CSS-селектора |
| P0, готово | Взаимоисключающий опрос, очередь и проверка результатов | M | Идемпотентный конечный результат | Обрыв связи после действия не теряет результат |
| P0, готово | Снимок выбранной вкладки и полноразмерный снимок через CDP | S | Разрешение `debugger` | Фоновая вкладка даёт собственный PNG |
| P0, следующий | Аренда доставки, подтверждение, номер попытки, повторная выдача и ключ идемпотентности | L | Версионированный протокол, классы действий | Падение исполнителя не оставляет команду навечно выданной и не дублирует опасный побочный эффект |

| P3 | Адаптер MCP и типизированный набор Python | M | Стабильная схема версии 1+ | Контрактные тесты подтверждают равенство CLI, Python и MCP |
| P3 | Пакет оценки в стиле BrowserGym и WebArena | L | Сквозной стенд, артефакты | Регрессия измеряет итог задачи, задержку и восстановление, а не только успех команды |

## Метрики успеха

Для каждого выпуска следует хранить минимум:

- успех команды и успех конечного состояния отдельно;
- p50/p95 времени от постановки до выдачи, длительность действия и всей задачи;
- долю восстановленных селекторов и ссылок;
- число повторов, повторных выдач и предотвращённых дубликатов;
- устаревших клиентов, истёкших аренд и возраст очереди результатов;
- размер снимка в байтах и элементах, оценку токенов агента;
- классы ошибок: не найдено, неоднозначно, не готово, навигация, разрешение,
  транспорт и правило безопасности;
- долю запусков с достаточным пакетом доказательств.

Целевая проверка P0/P1 — повторить набор динамических тестовых страниц не менее
100 раз без нестабильных сбоев, включая повторную отрисовку, перекрытие,
отложенное включение, фоновую вкладку и кратковременную недоступность хаба.
Числовые целевые показатели следует зафиксировать после
первого измерительного прогона, а не угадывать заранее.

## Модель безопасности

Проект остаётся локальным доверенным операторским инструментом. Ни MCP, ни
автоматизация браузера сами по себе не являются песочницей или границей
безопасности.

До удалённого доступа или многопользовательского режима обязательны:

- запрет токена в строке запроса и строгое правило источника;
- TLS/mTLS или локальный аутентифицированный туннель;
- отдельные учётные данные и области возможностей для каждого агента;
- списки разрешённых и запрещённых доменов;
- скрытие cookie, заголовков `Authorization`, секретов форм и снимков;
- отдельное подтверждение `run_script`, file upload/download, credential и
  междоменных действий;
- шифрование состояния сессии и ограниченный срок хранения артефактов.
