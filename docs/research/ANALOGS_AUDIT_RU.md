# Сравнение Site Control Kit с открытыми решениями

Дата исследования: 24 июля 2026 года.

Использованы первичные источники: официальные репозитории и документация
проектов. Маркетинговые измерения помечены как заявления авторов и не
считаются независимым тестом.

## Краткий вывод

Ни одно рассмотренное решение не закрывает ровно нашу задачу: безопасно
управлять уже открытым локальным браузером через простой хаб с журналируемой
доставкой и владением вкладкой.

Site Control Kit сильнее в:

- явном жизненном цикле `lease -> ack -> running -> result`;
- защите от просроченного результата и двойного опасного действия;
- блокировках вкладок между агентами;
- локальном outbox результата после падения service worker;
- русском операторском контуре.

Он слабее зрелых систем в:

- скорости доставки из-за polling;
- полноте действий, профилей, прокси, скачивания и API диалогов;
- HAR, трассировке и видео;
- мультибраузерности;
- готовых SDK и облачном масштабировании;
- степени модульности двух крупных файлов.

## Playwright

[Playwright](https://github.com/microsoft/playwright) — зрелая библиотека и
средство запуска тестов с ядром на TypeScript/Node.js и API для нескольких
языков.

Сильные стороны:

- Chromium, Firefox и WebKit, а также Chrome и Edge
  ([официальная матрица](https://playwright.dev/docs/browsers));
- строгие семантические локаторы, повторный поиск после перерисовки и
  `FrameLocator`
  ([локаторы](https://playwright.dev/docs/locators));
- автоматические проверки единственности, видимости, стабильности,
  доступности и получения событий
  ([auto-waiting — автоматические ожидания](https://playwright.dev/docs/actionability));
- изолированные BrowserContext, несколько страниц и ролей;
- storage state для cookies, localStorage и IndexedDB
  ([авторизация](https://playwright.dev/docs/auth));
- прокси HTTP/SOCKS, скачивания, HAR, видео и трассировка
  ([BrowserType](https://playwright.dev/docs/api/class-browsertype),
  [tracing](https://playwright.dev/docs/api/class-tracing)).

Ограничения для нашей задачи:

- обычная библиотечная команда предполагает живое соединение с браузером, а не
  журналируемую доставку через падение отдельного расширения;
- `connectOverCDP` только для Chromium и, по документации, менее полноценен,
  чем родной протокол Playwright;
- нет нашей модели аренды, dead letter и владения существующей вкладкой между
  независимыми агентами.

Что заимствуем: `BrowserAdapter` — общий браузерный адаптер, контексты,
локаторы, проверку готовности элемента, трассировку и сохранённое состояние
авторизации. Playwright — лучший кандидат на второй движок, но не замена нашему
хабу.

## Selenium

[Selenium](https://github.com/SeleniumHQ/selenium) использует стандарт
WebDriver и WebDriver BiDi, поддерживает несколько языков, локальный запуск и
Grid.

Сильные стороны:

- Chrome, Edge, Firefox и Safari
  ([поддерживаемые браузеры](https://www.selenium.dev/documentation/webdriver/browsers/));
- зрелая удалённая инфраструктура и Docker Grid;
- стабильные window handle для вкладок и окон
  ([окна и вкладки](https://www.selenium.dev/documentation/webdriver/interactions/windows/));
- явные и настраиваемые ожидания
  ([стратегии ожидания](https://www.selenium.dev/documentation/webdriver/waits/)).

Слабые стороны:

- разработчик сам выбирает и сочетает ожидания; документация отдельно
  предупреждает о гонках и смешивании implicit/explicit waits;
- API ориентирован на тестовый код, а не на компактный контекст LLM;
- нет встроенного семантического snapshot/ref протокола и нашей
  идемпотентности внешнего действия.

Что заимствуем: независимый от браузера интерфейс, BiDi и модель удалённого
Grid после закрытия локального P0/P1.

## Puppeteer

[Puppeteer](https://github.com/puppeteer/puppeteer) — JavaScript API для Chrome
и Firefox через CDP или WebDriver BiDi.

Сильные стороны:

- близкий к браузеру API и быстрый доступ к CDP;
- локаторы с автоматическим ожиданием нужного состояния
  ([взаимодействие со страницей](https://pptr.dev/guides/page-interactions));
- хорошая база для отладки Chromium.

Слабые стороны:

- основной стек Node.js;
- Firefox и BiDi развиваются, но экосистема сильнее всего в Chromium;
- сессии агентов, журналируемая доставка и управление конфликтами остаются
  задачей приложения.

Что заимствуем: узкий CDP‑адаптер и минимальный уровень абстракции, но не
вводим второе JavaScript‑ядро рядом с расширением без отдельной причины.

## Browser Use

[Browser Use](https://github.com/browser-use/browser-use) — Python/Rust
платформа, которая даёт LLM браузерный action space — набор действий.

Сильные стороны:

- агентный DOM вместо полного HTML;
- профили, подключение к существующему Chrome, CDP и несколько сессий;
- циклы восстановления после ошибки;
- быстрый CLI с постоянным фоновым процессом.

Авторы [заявляют](https://github.com/browser-use/browser-use/releases) около
`50 ms` задержки CLI и двукратное ускорение новой реализации. Это полезная
цель, но не независимый benchmark.

Ограничения:

- CLI на прямом CDP работает только с Chrome/Chromium;
- промышленное масштабирование, скрытность, CAPTCHA и прокси предлагаются
  прежде всего облачным продуктом;
- облачная сессия ограничивает одного агента на браузер
  ([описание cloud‑архитектуры](https://github.com/browser-use/browser-use/blob/main/CLOUD.md));
- нет публично заявленной модели lease/ack, равной нашей.

Что заимствуем: постоянный фоновый процесс, быстрый транспорт, компактное
состояние, профили и API восстановления.

## Stagehand

[Stagehand](https://github.com/browserbase/stagehand) сочетает обычный код,
естественный язык и резервный выбор с помощью ИИ.

Сильные стороны:

- `act`, `extract`, `observe` и многошаговый агент;
- кэширование успешных действий;
- автоматическое восстановление после изменения сайта;
- возможность сначала показать действие, затем выполнить;
- CDP‑движок и интеграция с Browserbase.

Ограничения:

- лучший режим требует LLM и часто облачной инфраструктуры;
- выбор с помощью ИИ повышает стоимость и недетерминированность;
- TypeScript‑стек и высокоуровневая задача не решают надёжную доставку между
  нашим хабом и уже открытым браузером.

Что заимствуем: разделение «наблюдать → предложить → действовать → проверить»,
кэш проверенных локаторов и явный резервный ИИ-путь только после
детерминированного провала.

## agent-browser

[agent-browser](https://github.com/vercel-labs/agent-browser) — CLI для агентов
с постоянным браузерным фоновым процессом и Rust-сервером.

Сильные стороны по
[официальному README](https://github.com/vercel-labs/agent-browser/blob/main/README.md):

- snapshot/ref‑поток и семантические локаторы;
- стабильные идентификаторы и пользовательские метки вкладок;
- несколько изолированных сессий;
- профили, storage state и шифрование AES‑256‑GCM;
- HAR, сеть, скачивания, прокси, панель управления и несколько облачных
  провайдеров;
- подключение к существующему Chrome.

Ограничения:

- основная локальная реализация ориентирована на Chromium/Lightpanda и прямое
  управление daemon;
- богатый единый CLI увеличивает поверхность API;
- модель конфликтов нескольких агентов на одной внешней вкладке отличается от
  нашей явной tab lock.

Что заимствуем в первую очередь: стабильные идентификаторы и метки вкладок,
шифрованное состояние авторизации, HAR, панель управления и модуль провайдера.

## Skyvern

[Skyvern](https://github.com/Skyvern-AI/skyvern) — Python/TypeScript-система
сценарной автоматизации поверх Playwright, большой языковой модели и
компьютерного зрения.

Сильные стороны:

- работа с незнакомыми и динамическими сайтами без заранее заданного XPath;
- конструктор сценариев, API и интерфейс;
- структурированное извлечение, проверка и скачивание;
- вход через сервис учётных данных, Bitwarden/1Password и двухфакторную
  аутентификацию;
- локальный SQLite или PostgreSQL, облачное масштабирование.

Ограничения:

- тяжёлая инфраструктура и зависимость от моделей для основного преимущества;
- визуальное рассуждение медленнее и дороже детерминированного DOM-действия;
- лицензия AGPL‑3.0 требует отдельной юридической оценки;
- скрытность, прокси и CAPTCHA сильнее представлены в облаке.

Что заимствуем позднее: резерв компьютерного зрения, адаптер учётных данных и
проверку сценария, но только после детерминированного P1/P2.

## Практическое решение

1. Не заменять хаб Playwright или agent-browser: они не дают нашей гарантии
   доставки и владения вкладкой.
2. Выделить `BrowserAdapter`, сохранив extension‑backend первым.
3. Добавить Playwright вторым backend для изолированных контекстов, профилей и
   Firefox.
4. Перенести идеи stable tab labels, storage encryption, HAR и long polling.
5. Оставить компьютерное зрение и языковую модель последним резервным уровнем
   после строгого локатора и проверки результата.

## Методологическое ограничение

Скорость проектов не сравнивалась на одном стенде. Публичные цифры зависят от
браузера, модели, сети и способа запуска. Для выбора реализации нужен отдельный
сравнительный тест: 100 чтений, 100 кликов, 20 навигаций, 20 перезапусков и
одинаковая тестовая страница.
